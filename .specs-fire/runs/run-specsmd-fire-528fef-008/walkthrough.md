# Implementation Walkthrough: Create CA purpose selector

## Summary

The Create CA page now asks what the CA is for. A required selector offers Root, TLS/SSL, User login, S/MIME, IoT devices, 802.1x/RADIUS and Custom (marked discouraged). Choices the chosen parent cannot issue are disabled with a reason, a plain-language summary explains what the CA will allow, and the purpose is saved with the CA, which the service turns into a CA certificate with the right usages and path length.

## Structure Overview

The option rules live in `CaProfileCatalog` (`Resolve`, `CheckIssuer`, `CheckCanIssueCas`, `EvaluateForParent`) and are used by both the page and `CertificateAuthorityService`, so the UI and the server agree. The page only renders the options and keeps its state consistent when the parent changes.

## Key Implementation Details

### 1. What the user sees

| Parent | Purposes offered |
|---|---|
| None | All seven |
| A Root CA | Everything except Root |
| A TLS/SSL CA with no parent | TLS/SSL only |
| An IoT CA with no parent | TLS/SSL, IoT, 802.1x |
| A purpose CA that itself has a parent | None (it is disabled in the parent list) |
| An older CA with no purpose ("Legacy") | Everything except Root |

### 2. Is Issuer

Off and locked for Root; on by default for every other purpose, because the Create Certificate page only lists CAs marked as issuers.

### 3. Custom

Discouraged and limited until `custom-ca-usages-ui` lands: standalone it creates a CA with the previous broad usages; under a restricted parent it is disabled.

## Decisions Made

| Decision | Choice | Rationale |
|----------|--------|-----------|
| Where option rules live | Core library, shared with the service | Testable, and the UI cannot disagree with the server |
| Default purpose | None, required | A deliberate choice per CA |
| Parent list | Shows purposes; disables CAs that cannot issue CAs | Avoids dead ends |
