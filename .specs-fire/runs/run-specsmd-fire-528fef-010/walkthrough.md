# Implementation Walkthrough: Create Certificate follows the issuing CA profile

## Summary

On the Create Certificate page, choosing a purpose CA as the issuer removes the Key Usage and Extended Key Usage pickers. The CA's usages are applied automatically and a short note shows what they are. Self-signed certificates and legacy CAs keep the pickers. CAs that never issue leaf certificates, such as Root, are no longer offered as issuers, and each CA in the list now shows its purpose.

## Structure Overview

`CaProfile.LocksLeafUsages` decides whether the usages are fixed. The page resolves the selected issuer's profile; when it locks usages, the page copies the profile's leaf key usages and extended key usages into the view model and shows a note instead of the pickers. When the issuer changes to self-signed or to an unlocked CA, the editable defaults are restored.

## Key Implementation Details

### 1. What the user sees

| Issuer | Usages section |
|---|---|
| Self Signed Certificate | Both pickers, with the same defaults as before |
| Purpose CA (TLS/SSL, User login, S/MIME, IoT, 802.1x/RADIUS) | No pickers; a note, for example "Usages are set by the TLS/SSL CA. Key usages: Digital Signature, Key Encipherment. Extended key usages: Server Authentication." |
| Legacy CA with no purpose | Both pickers, as before |
| Root (not offered; warning if reached) | A warning that a Root CA never issues certificates directly |

### 2. Why values are copied into the view model

The submit code already reads the selected usages from the view model. Filling them from the profile means the request is built exactly as before, and the server's profile check from the previous run accepts it because it is the CA's own profile.

## Decisions Made

| Decision | Choice | Rationale |
|----------|--------|-----------|
| Show the usages or hide them | A read-only note (chosen by the user) | Users can see what the certificate will carry without being able to change it |
| Where the rule lives | `CaProfile.LocksLeafUsages` in core | One tested rule, shared with any future screen |
