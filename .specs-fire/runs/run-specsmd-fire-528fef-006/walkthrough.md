# Implementation Walkthrough: Persist CA purpose

## Summary

The CA record can now carry a purpose and, for Custom CAs, the key usages and extended key usages the user chose. Both the API contract and the Mongo model have the new fields, and they map in both directions. Existing CAs have none of them and load as Custom, so nothing needs migrating. No code sets the purpose yet.

## Structure Overview

`CertificateAuthority` (contract) gains `Purpose`, `CustomKeyUsages` and `CustomExtendedKeyUsages`. `CertificateAuthorityModel` gains matching Mongo elements `purpose`, `custom_key_usages` and `custom_ex_key_usages`. `ModelMapProfile` maps them with AutoMapper, plus one rule that keeps the Custom lists null instead of empty.

## Key Implementation Details

### 1. Storage format

The purpose is stored as a string (`"TlsSsl"`) and shown in JSON by name. Key usages are stored as their names, matching how certificates store theirs. Reordering the enum later therefore cannot change what a stored CA means.

### 2. Legacy CAs

A document without the new elements loads with a null purpose, and `CaProfileCatalog.Get(null)` resolves that to Custom (unrestricted). Nothing is rewritten.

### 3. Why the mapping rule exists

AutoMapper turns a null collection into an empty one. Without the rule, saving a CA with no Custom usages would write empty arrays, and reading a legacy CA would produce empty lists instead of null. The plan expected no mapping change; the test found this and the rule fixes it.

## Decisions Made

| Decision | Choice | Rationale |
|----------|--------|-----------|
| Purpose storage | String in Mongo, name in JSON | Safe against enum reordering |
| Null versus empty | Keep null when unset | Distinguishes legacy CAs and keeps documents tidy |
| Index | None | Nothing queries by purpose |

## Deviations from Plan

One: the plan expected no change to `ModelMapProfile`. A test showed AutoMapper turns null lists into empty ones, so I added a small `AfterMap` rule scoped to the CA map.
