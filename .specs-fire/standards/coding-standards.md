# Coding Standards

## Formatting

- **Tool**: `dotnet format`
- Allman bracing, file-scoped namespaces

## Naming

| Element | Convention | Example |
|---------|------------|---------|
| Classes, methods, properties | PascalCase | `CertificateRevokeService` |
| Locals, parameters | camelCase | `serialNumber` |
| Private fields | `_` + camelCase | `_repository` |
| Interfaces | `I` prefix | `ICertificateService` |

Files are named after the primary type (e.g. `CertificateService.cs`).

## Project Structure

```
src/library/core      Contracts, interfaces, Result<T>, config, view models
src/library/data      MongoDB models, repositories, mapping
src/library/service   Business logic services
src/web               Blazor + API host
src/setup             Setup tooling
src/test              NUnit tests
Notary.AppHost        Aspire host
Notary.ServiceDefaults
```

## Modern C#

- Primary constructors, collection expressions, pattern matching
- Positional `record` types for immutable DTOs and configuration

## Error Handling

- Use the `Result<T>` pattern (`src/library/core/Result.cs`) for expected business/validation failures; do not throw for those
- Exceptions (`NotaryException`) only for unexpected/exceptional conditions

## Async and Performance

- Always pass `CancellationToken` through async calls
- Prefer `ValueTask` for hot paths that often complete synchronously
- Use `ReadOnlySpan<T>`/`Memory<T>` for byte/string parsing; `ArrayPool<T>` for large temporary buffers in hot paths

## APIs

- Prefer Minimal APIs for new endpoints unless model binding is too complex

## Logging

- log4net; never log private keys, passwords or tokens

## Anti-Patterns

- Throwing exceptions for validation failures
- Hardcoded secrets
- Async calls that drop the CancellationToken
