# System Architecture

## Overview

Notary is a PKI service: it manages certificate authorities, issues and revokes certificates, and publishes RFC 5280 CRLs. Used for a Raspberry Pi server farm.

## Architecture Pattern

Layered monolith: `core` (contracts, Result<T>) → `data` (MongoDB repositories) → `service` (business logic) → `web` (ASP.NET Core API + Blazor UI). Autofac wires services via registration modules.

## Components

- **Notary (core)**: interfaces, view models, configuration, algorithm/format enums, `Result<T>`
- **Notary.Data**: Mongo models, repositories, AutoMapper profile
- **Notary.Service**: `CertificateAuthorityService`, `CertificateService`, `CertificateRevokeService`, `AsymmetricKeyService`, etc.
- **Notary.Web**: API endpoints and MudBlazor UI, Auth0/OIDC authentication
- **Notary.Setup**: setup tooling
- **Notary.AppHost / ServiceDefaults**: Aspire orchestration for local dev (Mongo + web)

## Data Flow

UI/API request → service (validation, crypto via BouncyCastle) → repository → MongoDB. CRLs are generated from revocation records and served at a CRL distribution point URL derived automatically.

## Technology Stack

| Layer | Technology | Purpose |
|-------|------------|---------|
| UI | Blazor + MudBlazor | Management interface |
| API | ASP.NET Core | Programmatic access |
| Crypto | BouncyCastle | X.509, CRLs |
| Data | MongoDB | Persistence |
| Auth | Auth0 / Microsoft.Identity.Web | Authentication |
| Hosting | Docker, Aspire | Deployment, local orchestration |

## Constraints

- Docker unavailable on the dev machine; CI builds images
- Targets small ARM hardware (Raspberry Pi), so keep resource use modest

## Key Decisions

| Decision | Choice | Rationale |
|----------|--------|-----------|
| Revocation | RFC 5280 CRLs | See `docs/plan/notary-revocation-plan.md` |
| Error handling | `Result<T>` | Avoid exceptions for expected failures |
